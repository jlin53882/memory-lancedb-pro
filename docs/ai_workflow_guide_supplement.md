## 一、本日新增經驗

### 事件：批次文字替換破壞 Python f-string 語法

**問題描述**：
- 嘗試用批次腳本將 `print()` 替換成 `config.log_print()`
- 過程中 f-string 格式被破壞（例如 `{code}` 變成 `{f'code'}` 或 `{f"code"}`）
- 導致 20+ 處 SyntaxError，需要手動逐一修復

**教訓**：
- ❌ **避免用批次腳本修改 Python 程式碼**（尤其是涉及 f-string 或特殊字元時）
- ✅ **逐檔案手動處理**，每次修改後立即驗證
- ✅ **修改後立即執行 `python -m py_compile` 確認語法正確**

## 二、Stock Trading 專案問題修復流程

### 問題清單與修復方式

| 問題類型 | 檔案數 | 修復方式 |
|----------|--------|----------|
| Bare except | 10 處 | 改為 `except Exception as e:` + `log_warning()` |
| API Key 硬編碼 | 2 處 | 改為 `os.getenv()` + `.env` |
| Yahoo API 回傳類型不穩定 | 1 處 | 新增 `safe_get_first()` 函數 |
| 缺少 logs 資料夾 | - | 自動建立 `LOGS_PATH.mkdir()` |
| f-string 語法錯誤 | 20+ 處 | **慘痛教訓：不要用批次腳本** |

### 正確的修改流程

```
1. 閱讀原始程式碼（用 read 工具）
   ↓
2. 理解上下文
   ↓
3. 小幅修改（每次 1-2 處）
   ↓
4. 驗證語法：python -m py_compile <檔名>
   ↓
5. 測試執行：uv run python <檔名>
   ↓
6. 如有問題立刻還原 / 手動修復
```

## 三、本日學習的重點原則

### 新增原則：批次修改的風險

```
❌ 避免
print() → config.log_print()  # 批次替換
大量文字取代              # 容易出錯

✅ 正確
每次只改 1-2 處
改完立刻編譯驗證
```

### 其他原則（延續）

1. **驗證優先** - 用工具確認事實
2. **依賴用 uv** - `uv sync`
3. **修改前備份**
4. **測試驗證** - `pytest` 或執行一次
