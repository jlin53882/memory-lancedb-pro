# Minecraft Translation Flet - UI 優化建議設計稿

> 設計者：Claw  
> 日期：2026-03-15  
> 版本：v1.0

---

## 1. 現況分析

### 1.1 現有 View 結構

| View | 功能 | 程式碼規模 |
|------|------|-----------|
| TranslationView | 翻譯工作台（FTB/KubeJS/MD） | ~400 行 |
| CacheView | 快取管理（總覽/查詢/分片） | **~2000+ 行** |
| ConfigView | 系統設定 | ~400 行 |
| RulesView | 替換規則管理 | ~500 行 |
| 其他 Views | QC/Lookup/Bundler/Extractor 等 | 各 100-300 行 |

### 1.2 現有 UI 問題點

| 問題分類 | 具體問題 | 嚴重程度 |
|----------|----------|----------|
| **資訊密度** | CacheView 單頁承載過多資訊（總覽+查詢+分片+歷史），使用者難以聚焦 | 🔴 高 |
| **視覺層次** | 缺乏統一的「區塊標題樣式」，不同頁面視覺不一致 | 🟡 中 |
| **交互效率** | 無法快速跳轉到指定頁面/功能，需多次點擊 NavigationRail | 🟡 中 |
| **反饋機制** | 長時間操作（reload/save）缺乏進度條，只有狀態文字 | 🟡 中 |
| **鍵盤操作** | 完全沒有鍵盤快捷鍵，熟練使用者操作效率低 | 🟡 中 |
| **維護性** | CacheView 超過 2000 行，新增功能困難 | 🔴 高 |
| **響應式** | 固定寬高設計，小螢幕體驗差 | 🟢 低（目前非主要目標） |

## 2. 優化方案

### 2.1 優化一：NavigationRail 增強 - 快速跳轉面板

**問題**：使用者需要在 11 個 View 之間跳轉，點擊效率低。

**設計**：

```
┌─────────────────────────────────────────────────────┐
│  [≡]  Minecraft 模組包繁體化工具        [🌙]        │
├──────┬──────────────────────────────────────────────┤
│      │  ┌─ 快速跳轉 ─────────────────────────────┐  │
│ [📁] │  │  🔍 輸入頁面名稱或關鍵字...          │  │
│ 設定  │  ├──────────────────────────────────────┤  │
│      │  │  ► 設定                    ⌘1         │  │
│ [📋] │  │    規則                    ⌘2         │  │
│ 規則  │  │    快取管理                ⌘3         │  │
│      │  │    翻譯工具                ⌘4         │  │
│ [💾] │  │    ...                                 │  │
│ 快取  │  └────────────────────────────────────────┘  │
│      │                                               │
│  ... │           （點擊 NavigationRail 展開）        │
└──────┴──────────────────────────────────────────────┘
```

**實現方式**：
- 在 NavigationRail 上增加「搜尋圖標」，點擊彈出快速跳轉面板
- 支援模糊搜尋（fuzzy search）
- 顯示鍵盤快捷鍵綁定（⌘1-⌘9）

**為什麼這樣設計**：
- 減少滑鼠移動距離，符合「三擊原則」
- 視覺上不佔用主要空間，使用時才展開

---

### 2.2 優化二：統一區塊卡片樣式 + 收合功能

**問題**：資訊密度過高，使用者難以找到目標資訊。

**設計**：

```
┌─────────────────────────────────────────────────────┐
│  📦 快取總覽                        [▼ 收合] [⚡]  │
├─────────────────────────────────────────────────────┤
│  總筆數: 12,450  |  有變更: 3  |  最近更新: 15:30  │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 45%                │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  🔍 快取查詢                      [▶ 展開] [⚡]     │
├─────────────────────────────────────────────────────┤
│  （收合時只顯示標題，點擊展開詳細內容）               │
└─────────────────────────────────────────────────────┘
```

**實現方式**：
- 擴展 `styled_card` 元件，增加 `collapsible` 參數
- 收合狀態預設保存在 `config.json`
- 每個卡片右上角提供「閃電」快捷操作（常見操作）

**為什麼這樣設計**：
- 減少視覺負擔，讓使用者專注於當前任務
- 常用功能一眼可達

---

### 2.3 優化三：操作反饋增強 - 進度條與 Toast 統一化

**問題**：長時間操作（如 reload/save/rebuild index）只有靜態文字，使用者不知道還要等多久。

**設計**：

```
┌─────────────────────────────────────────────────────┐
│  執行狀態                                            │
│  ━━━━━━━━━━━━━━━━━━━━━━━━░░░░░░░░░░░ 65%           │
│  正在寫入快取分片... (1,234 / 1,900)                │
│  ⏱ 預估剩餘時間：12 秒                              │
│           [⟳ 取消]                                  │
└─────────────────────────────────────────────────────┘
```

**實現方式**：
- 建立統一的 `ProgressCard` 元件
- 支援：進度百分比、ETA 計算、取消按鈕
- 整合到 CacheView、TranslationView 等長時間操作頁面

**為什麼這樣設計**：
- 降低使用者焦慮感
- 提供取消功能，避免誤操作後只能等待

---

### 2.4 優化四：鍵盤快捷鍵系統

**問題**：完全沒有鍵盤導航，熟練使用者操作慢。

**設計**：

| 快捷鍵 | 功能 | 適用頁面 |
|--------|------|----------|
| `⌘1-9` | 快速跳轉到指定 View | 全域 |
| `⌘F` | 聚焦搜尋框 | 全域 |
| `⌘S` | 儲存當前操作 | Config/Rules |
| `⌘R` | 重新整理/重新載入 | 全域 |
| `⌘,` | 開啟設定頁面 | 全域 |
| `Esc` | 關閉彈出視窗/取消操作 | 全域 |
| `Tab` | 在輸入框之間導航 | 表單頁面 |
| `Enter` | 確認操作 | 對話框 |

**實現方式**：
- 在 `main.py` 的 `page.on_keyboard_event` 處理全域快捷鍵
- 各 View 可註冊自己的快捷鍵處理

**為什麼這樣設計**：
- 符合專業軟體操作習慣
- 大幅提升操作效率

---

### 2.5 優化五：代碼重構 - CacheView 拆分

**問題**：CacheView 超過 2000 行，維護困難。

**設計**：

```
app/views/cache_manager/
├── __init__.py
├── cache_overview_panel.py     # ✅ 已拆分
├── cache_query_panel.py        # [NEW] 查詢區域
├── cache_shard_panel.py        # [NEW] 分片區域  
├── cache_history_panel.py      # [NEW] 歷史記錄面板
├── cache_actions.py            # ✅ 已拆分
├── cache_controller.py         # [NEW] 控制器
├── cache_presenter.py         # [NEW] 呈現邏輯
└── cache_state.py              # ✅ 已拆分
```

**實現方式**：
- 採用 MVP 模式：Model-View-Presenter
- Controller 負責協調各 Panel
- 每個 Panel 控制在 300 行以內

**為什麼這樣設計**：
- 單一職責原則
- 未來新功能好加入
- 測試更容易

---

### 2.6 優化六：統一的 Empty / Loading / Error 狀態

**問題**：各頁面處理方式不一致。

**設計**：

```python
# app/ui/components.py 新增

def empty_state(
    icon: str,
    title: str,
    message: str,
    action_button: ft.Control | None = None
) -> ft.Container:
    """統一的空狀態顯示"""
    ...

def loading_state(
    message: str = "載入中...",
    show_spinner: bool = True
) -> ft.Container:
    """統一的載入狀態顯示"""
    ...

def error_state(
    icon: str,
    title: str,
    message: str,
    retry_button: ft.Control | None = None
) -> ft.Container:
    """統一的錯誤狀態顯示"""
    ...
```

**為什麼這樣設計**：
- 視覺一致性
- 減少重複代碼

## 5. 風險與限制

| 風險 | 影響 | 緩解措施 |
|------|------|----------|
| 快捷鍵與系統衝突 | 使用體驗差 | 預設使用 `⌘` (Command) 而非 `Ctrl` |
| 重構破壞現有功能 | 系統不穩定 | 每次重構後執行完整測試 |
| 進度估算不準確 | 進度條誤導 | 初期使用「 indeterminate」模式 |
